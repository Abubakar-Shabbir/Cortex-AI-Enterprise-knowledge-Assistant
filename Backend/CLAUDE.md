# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Django-based RAG (Retrieval-Augmented Generation) document assistant. Users upload documents (PDF/DOCX/TXT), the app extracts, cleans, and chunks the text, embeds each chunk, stores vectors in PostgreSQL (via `pgvector`), extracts entities/relationships into a per-user knowledge graph, and answers questions using hybrid (vector + BM25 + graph) retrieval passed as context to Google Gemini.

Django project name is `myproject`; the single app is `RAG` (note the uppercase app label — imports/migrations reference `RAG`, not `rag`).

## Commands

Run all commands from the repo root (where `manage.py` lives).

```
python manage.py runserver          # start dev server
python manage.py makemigrations RAG # create migrations after model changes
python manage.py migrate            # apply migrations
python manage.py test RAG           # run tests
python manage.py createsuperuser    # for /admin access
pip install -r requirements.txt     # install deps
```

There is no configured linter/formatter in the repo.

`RAG/tests.py` deliberately mixes two base classes: plain `unittest.TestCase` for pure-logic tests (normalization, JSON parsing, mocked-LLM extraction) that need no database, and `django.test.TestCase` for tests that touch models. This matters because `django.test.TestCase.setUpClass` opens a DB transaction unconditionally, even for a test body that never queries anything — so *any* `django.test.TestCase` in the suite requires a reachable Postgres (with the `vector` extension available to the ephemeral test DB) for `manage.py test` to run at all. If you only need to check the pure-logic tests without a DB, load Django (`django.setup()`) and run those specific `unittest.TestCase` classes directly instead of through `manage.py test`.

**`requirements.txt` was rewritten (Sprint 10)** to a curated, UTF-8, top-level-only list (it was previously UTF-16-encoded and missing several packages the code actually imports). It's still worth knowing the `fitz` import is fragile — a same-named but unrelated `fitz` package (a neuroimaging workflow tool, unrelated to PyMuPDF) can end up on `sys.path` in a shared/global Python environment and shadow PyMuPDF, breaking the import with `ModuleNotFoundError: No module named 'frontend'`; if that happens, `pip uninstall fitz frontend && pip install pymupdf`. If you regenerate this file with a raw `pip freeze`, check the environment isn't polluted with unrelated packages first (a global/shared env can easily accumulate dozens of packages this project never imports) — prefer curating top-level direct imports over dumping a freeze verbatim.

## Environment configuration

Settings load from a `.eee` file at the repo root via `django-environ` / `python-dotenv` (`myproject/settings.py`). Required variables:

- `SECRET_KEY`, `DEBUG`
- `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT` — PostgreSQL connection (the only supported DB backend; `ENGINE` is hardcoded to `django.db.backends.postgresql`)
- `GEMINI_API_KEY` — Gemini provider key, used by `RAG/services/llm_client.py`
- Optional, with defaults in `settings.py`: `TOP_K` (3), `EMBEDDING_MODEL` (`all-MiniLM-L6-v2`), `LLM_MODEL` (`gemini-2.0-flash`)
- LLM provider selection (`llm_client.py`, see LLM Client section below): `LLM_PROVIDER` (default `openrouter`), `LLM_FALLBACK_ENABLED` (`False`), `LLM_REQUEST_TIMEOUT` (30s), `LLM_MAX_RETRIES` (1), `OPENROUTER_API_KEY`/`OPENROUTER_MODEL`, `GROQ_API_KEY`/`GROQ_MODEL`, `ANSWER_MAX_TOKENS` (1024)
- S3-compatible file storage (see Deployment below): `USE_S3_STORAGE` (`False`); when `True`, requires `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_STORAGE_BUCKET_NAME`, `AWS_S3_ENDPOINT_URL`, optional `AWS_S3_REGION_NAME` (`us-east-1`)
- AI Tasks (see AI Tasks section below): `AI_TASKS_MAX_DOCUMENTS` (100)
- Optional Advanced Retrieval flags (Sprint 6), all with defaults in `settings.py`: `ENABLE_QUERY_EXPANSION` (`False`), `ENABLE_HYDE` (`False`), `ENABLE_MULTI_QUERY` (`False`), `ENABLE_DYNAMIC_TOP_K` (`True`), `DYNAMIC_TOP_K_MAX` (10), `MULTI_QUERY_VARIANTS` (3) — see the Advanced Retrieval section below for why the LLM-cost features default off
- Optional Reranking flags (Sprint 7): `ENABLE_RERANKER` (`False`), `RERANKER_MODEL` (`BAAI/bge-reranker-base`), `RERANKER_CANDIDATE_MULTIPLIER` (3) — see the Reranking section below
- Optional Context Compression flags (Sprint 8): `ENABLE_CONTEXT_COMPRESSION` (`False`), `CONTEXT_COMPRESSION_THRESHOLD` (`0.92`) — see the Context Compression section below
- Answer Generation (Sprint 9): `ANSWER_TEMPERATURE` (`0.2`) — see the Answer Generation section below
- Background Task Execution (free-tier refactor): `BACKGROUND_WORKER_THREADS` (`4`), `ENABLE_ASYNC_PROCESSING` (`False`), `DJANGO_LOG_LEVEL` (`INFO`) — see the Background Task Execution and Monitoring sections below

**The PostgreSQL database must have the `vector` extension enabled manually** (`CREATE EXTENSION IF NOT EXISTS vector;`) — no migration does this, it's a prerequisite the migrations assume is already in place. `settings_view` / `get_system_status()` checks this live and surfaces it on the Settings page.

**Settings.py gotchas** (non-obvious, easy to trip over when touching chunking/embeddings):
- `CHUNK_SIZE` is read from the environment near the top of `settings.py`, then unconditionally **overwritten to the literal `800`** near the bottom of the same file. The env var currently has no effect; `CHUNK_OVERLAP` (150) is a plain hardcoded constant, not env-driven at all.
- `EMBEDDING_DIMENSION` is a hardcoded `1024`, independent of `EMBEDDING_MODEL`. The default `EMBEDDING_MODEL` (`all-MiniLM-L6-v2`) actually produces 384-dim vectors — mismatched with the `VectorField(dimensions=settings.EMBEDDING_DIMENSION)` on `ChunkEmbedding`. If you change `EMBEDDING_MODEL`, you must also update `EMBEDDING_DIMENSION` and the migration for `ChunkEmbedding.embedding` to match the real output dimension of that model, or embedding inserts will fail.
- `LLM_MODEL` **is now live** (Sprint 9) and has since been superseded by a full multi-provider client. `llm_service.py` no longer talks to Gemini directly or via a `gemini_client` singleton — it calls `RAG/services/llm_client.py`'s module-level `LLMClient`, which wraps three provider adapters (`GeminiClient` on the `google.genai` SDK, `OpenRouterClient`/`GroqClient` on a shared OpenAI-compatible REST client) behind one interface. `settings.LLM_PROVIDER` (default `openrouter`) picks the primary; when `settings.LLM_FALLBACK_ENABLED` is `True`, `LLMClient._build_chain()` appends the rest of a fixed `FALLBACK_PRIORITY` (`groq` → `openrouter` → `gemini`) that have a configured API key. A bad-key error (`LLMAuthError`) skips straight to the next provider instead of retrying; other errors retry up to `LLM_MAX_RETRIES` times on the same provider first. `generate_stream()` only has a fallback window before the first streamed chunk — a mid-stream failure propagates rather than silently restarting on another provider. `max_tokens` threads through every layer down to Gemini's `max_output_tokens` / the OpenAI-compatible `max_tokens` payload field; `llm_service.py` and `query_service.py` both pass `settings.ANSWER_MAX_TOKENS` (default 1024) into answer generation, but `llm_client.generate_json()` (used by graph extraction and other JSON-mode callers) does not accept `max_tokens`, only `temperature`.

## Architecture

### Upload pipeline — `upload_service.upload_document()`

1. `validation_service.validate_document()` — extension allowlist (`ALLOWED_FILE_EXTENSIONS`), max size (`MAX_FILE_SIZE`, 20 MB), non-empty, readable, non-blank filename.
2. `duplicate_service.check_duplicate()` — SHA-256 hash of the file contents, checked against `Document.file_hash` scoped to the current user; raises if already uploaded.
3. `metadata_service.extract_metadata()` — file name/extension/size.
4. Creates the `Document` row (file saved to `media/documents/`).
5. `document_processor.process_document()`:
   - `text_extractor.extract_text()` dispatches on extension: `.pdf` via PyMuPDF (`fitz`), `.docx` via `python-docx`, `.txt` via plain read.
   - Whitespace-normalizes the text.
   - `RecursiveCharacterTextSplitter` (langchain) splits it by `CHUNK_SIZE`/`CHUNK_OVERLAP` (characters, not words).
   - Each recursive chunk is further split by `semantic_chunk_service.semantic_chunk()` (langchain's `SemanticChunker`, percentile breakpoint, backed by a `HuggingFaceEmbeddings(EMBEDDING_MODEL)` instance separate from the one in `embedding_service.py`).
6. Each final chunk is saved as a `DocumentChunk` row (ordered by `chunk_number`).
7. `embedding_service.generate_embedding()` (SentenceTransformer, model = `settings.EMBEDDING_MODEL`, loaded once at import time) embeds each chunk.
8. `vector_service.save_embedding()` upserts a `ChunkEmbedding` row (one-to-one with `DocumentChunk`).
9. `graph_service.build_graph_for_chunk()` extracts entities/relationships from the chunk and merges them into the knowledge graph — see the Knowledge Graph section below. Wrapped in its own `try`/`except` in `upload_service.py`; a failure here is logged and swallowed, never fails the upload.
10. `Document.chunk_count` is updated to the final chunk total.

`RAG/utils/chunking.py`, `RAG/utils/file_parser.py`, and `RAG/utils/text_cleaner.py` are **dead code** — not imported anywhere in the current pipeline (extraction and chunking now live in `RAG/services/`). Only `RAG/utils/formatting.py` (`format_bytes`, `format_ms`) is actually used, by `stats_service.py` and `views.py`.

### Query pipeline — `query_service.answer_question()`

1. `retrieval_service.retrieve_chunks(question, user=None, filters=None, top_k=None)` runs **hybrid retrieval** across up to five sources, merged by `(document, chunk_number)`, optionally reranked (Sprint 7, see below), and capped to the effective `top_k`:
   - `vector_search()` — pgvector `L2Distance` similarity search over `ChunkEmbedding`.
   - `bm25_service.bm25_search()` — rank-bm25 `BM25Okapi`.
   - `graph_retrieval_service.graph_search()` — knowledge-graph lookup (see the Knowledge Graph section).
   - `hyde_search()` — Sprint 6, off by default (`settings.ENABLE_HYDE`). See Advanced Retrieval below.
   - `multi_query_service.multi_query_search()` — Sprint 6, off by default (`settings.ENABLE_MULTI_QUERY`). Imported *inside* `retrieve_chunks()`, not at module level, to break a circular import (`multi_query_service` reuses `retrieval_service.vector_search()` directly).
   - **Vector, BM25, and graph search are all scoped to the requesting user.** `retrieve_chunks()` resolves `accessible_document_ids = get_accessible_document_ids(user)` once (owned ∪ Organization Library ∪ shared documents — see Document Organization below) and threads it into every source; `vector_search()`/`hyde_search()` (via `_vector_similarity_search()`) and `bm25_search()` both fail closed (return `[]`) when `user` is `None`, the same precedent `graph_search()` already set. `user` stays an optional parameter for either function to be called standalone/in a script, but both real callers (`RAG/api/ask_views.py`'s `ask_view`, `RAG/views.py`'s `ask_ai`) always pass `user=request.user`, so a caller has to go out of its way (call one of these functions directly with `user=None`) to see cross-user results.
2. `query_service.answer_question()` optionally runs `context_compression_service.compress_context()` on the retrieved chunks (Sprint 8, off by default — `settings.ENABLE_CONTEXT_COMPRESSION`). This happens before anything downstream, so context, confidence, the search-method label, and the logged `QueryLog.sources` all reflect exactly what the LLM saw. See Context Compression below.
3. Retrieved (and, if enabled, compressed) chunks are rendered into a single numbered context string by `citation_service.build_cited_context()` (Sprint 9) — `"[1] (Document, chunk N):\n<content>"` blocks, in retrieval order — so the LLM has something concrete to cite.
4. `llm_service.generate_answer()` sends that numbered context + question to Gemini via `prompt_templates.build_answer_prompt()`, which instructs the model to answer only from the numbered sources, cite every claim inline as `[n]`, and reply with the fixed fallback (`prompt_templates.NOT_FOUND_ANSWER`) when unanswerable. Runs at `settings.ANSWER_TEMPERATURE` (default `0.2`, well below the provider default) as an additional hallucination-reduction lever. See Answer Generation below.
5. `citation_service.extract_citations()` parses which `[n]` markers actually appear in the answer, maps them back to the cited chunks, and annotates each cited entry in `retrieved_chunks` in place with `citation_number` (read by `ask_ai.html` to badge cited source cards).
6. `calculate_confidence(retrieved_chunks, answer=None, citation_count=None)` derives a 0–100 score from the L2 distances of `"vector"` and `"hyde"` chunks (both are genuine embedding-space distances; no distance evidence at all falls back to `40`). Because `embedding_service.generate_embedding()` always normalizes (`normalize_embeddings=True`), the score converts distance to cosine similarity exactly (`d² = 2(1 − cos_sim)`) rather than a flat `min(distance, 1.0)` cap, so a distance a bit past `1.0` — a routine, still-fairly-close match on unit vectors, whose real distance range is `0..2` — reads as a real, non-zero score instead of bottoming out at `0%`. Two Sprint 9 adjustments layer on top when `answer`/`citation_count` are passed (as `answer_question()` does): the fixed fallback answer forces confidence to `0` outright, and an answer that cited none of the retrieved sources discounts the score by 30%. Both parameters default to `None`/inert, so any caller passing only `retrieved_chunks` keeps the same (now-corrected) distance-based score.
7. `describe_search_method()` builds the `search_method` label (e.g. `"Hybrid (Vector + BM25)"`, `"Hybrid (Vector + BM25 + Graph + HyDE + Multi-query)"`) from whichever `search_type` values actually appear in the retrieved chunks, via the `SEARCH_TYPE_LABELS` list — extend that list alongside any new retrieval source rather than hardcoding a new fixed string.
8. Every question (when `user` is set) is persisted as a `QueryLog` row — question, answer, `sources` (JSON list of retrieved chunk dicts, now including `citation_number` on cited entries), `search_method`, `response_time_ms`, `confidence`. This is what powers Search History and Analytics; `source.search_type` and `stats_service`'s search-type breakdown are read generically from whatever strings appear, so a new retrieval source needs no template/analytics changes. `views.search_history`'s answered/unanswered classification now calls `prompt_templates.is_not_found_answer()` rather than keeping its own copy of the fallback substring.

### Advanced Retrieval (Sprint 6) (`RAG/services/{query_transform,query_expansion,hyde,retrieval_filters,dynamic_topk,multi_query}_service.py`)

Five composable retrieval enhancements, all reusing the existing `vector_search()`/`bm25_search()`/embedding/Gemini plumbing rather than duplicating it. **Design choice:** the three that cost an extra Gemini call per question (query expansion, HyDE, multi-query) default to **off** (`ENABLE_QUERY_EXPANSION` / `ENABLE_HYDE` / `ENABLE_MULTI_QUERY` = `False`), so the out-of-the-box request path and its latency/cost are unchanged from Sprint 5. Metadata filtering and dynamic top-k are local/free and are effectively always available (filtering is opt-in per call via `filters=None`; dynamic top-k defaults **on**, `ENABLE_DYNAMIC_TOP_K = True`). All five are fully implemented and unit-tested regardless of their default flag state — flip the relevant `.eee` flag to activate one, no code changes needed.

- **Query Expansion** (`query_expansion_service.expand_query()`) — asks Gemini for alternate phrasings via the shared `query_transform_service.generate_query_variants()`, then folds their distinct *words* into one enriched string appended to the original question. Used only to enrich the **BM25** query (`retrieve_chunks()`'s `lexical_query`) — vector search keeps embedding the raw question, since a keyword-stuffed sentence doesn't embed more accurately, only lexical matching benefits.
- **HyDE** (`hyde_service.generate_hypothetical_document()` + `retrieval_service.hyde_search()`) — asks Gemini to write a short hypothetical passage that would answer the question, embeds *that* instead of the question, and runs it through the same nearest-neighbor lookup as `vector_search()`. Both now share `retrieval_service._vector_similarity_search()` (extracted in this sprint) rather than duplicating the pgvector query. Tagged `search_type: "hyde"`.
- **Metadata Filtering** (`retrieval_filters.RetrievalFilters` / `apply_document_filters()`) — a frozen dataclass (`document_ids`, `file_types`, `uploaded_after`, `uploaded_before`) applied as Django queryset filters. Every retrieval function (`vector_search`, `hyde_search`, `bm25_search`, `graph_search`) takes the same `filters=None` keyword and calls `apply_document_filters(queryset, filters, document_field=...)` before slicing to `top_k` — a no-op when `filters` is `None`/empty. `RetrievalFilters.from_request()` builds one from loosely-typed request input (e.g. a POSTed `document_id` string) and degrades invalid input to "no filter" rather than raising. Exposed end-to-end via a "Search in" document dropdown on the Ask AI page (`views.ask_ai`, `templates/ask_ai.html`) — the only new UI surface Sprint 6 adds.
- **Dynamic Top-K** (`dynamic_topk_service.compute_dynamic_top_k()`) — a deliberately non-LLM, word-count-and-conjunction heuristic (see module docstring for why: retrieval depth is decided on *every* query, and this sprint already risks stacking multiple LLM calls per question). Replaces the fixed `settings.TOP_K` as `retrieve_chunks()`'s default depth unless a caller passes `top_k=` explicitly or `ENABLE_DYNAMIC_TOP_K` is `False`. Capped at `settings.DYNAMIC_TOP_K_MAX`.
- **Multi-query Retrieval** (`multi_query_service.multi_query_search()`) — RAG-Fusion style: reuses `generate_query_variants()` for `settings.MULTI_QUERY_VARIANTS` alternate phrasings, runs `vector_search()` + `bm25_search()` per *additional* variant (the original question is already covered by the primary hybrid search), and fuses the ranked lists with Reciprocal Rank Fusion (`_reciprocal_rank_fusion()`, standard `RRF_K = 60`). A failure on one variant's search is caught per-variant so it doesn't discard the others. Tagged `search_type: "multi_query"`.

`generate_query_variants()` (`query_transform_service.py`) is the one shared LLM-rewriting primitive behind both query expansion and multi-query retrieval — it's the only place that prompts Gemini for alternate phrasings, so the two features can't drift into duplicate prompt/parsing logic. It always returns the original question as `variants[0]`, and falls back to `[question]` on any failure.

Every new LLM-backed function in this section follows the same never-raise contract as `graph_extraction_service.extract_graph()` (Sprint 5): on any failure (missing API key, network/model error, malformed JSON) it logs and returns an empty/unchanged result, never propagates the exception. No new third-party dependencies were introduced.

### Reranking (Sprint 7) (`RAG/services/reranker_service.py`)

A BGE cross-encoder reranker re-scores the merged candidate list right before `retrieve_chunks()` returns, off by default (`settings.ENABLE_RERANKER`). Unlike the hybrid retrievers, which score each chunk independently (a pgvector distance, a BM25 score, an entity match), a cross-encoder scores each `(question, chunk)` pair jointly — a stronger relevance signal, at the cost of one local model inference pass per candidate chunk.

- `reranker_service.rerank_chunks(question, chunks, top_k=None)` runs `sentence_transformers.CrossEncoder(settings.RERANKER_MODEL)` (default `BAAI/bge-reranker-base`) over every candidate, sorts descending by score, and tags each result with an added `rerank_score` key — every existing key (including `search_type`) is preserved unchanged, so `calculate_confidence()`, `describe_search_method()`, `QueryLog.sources`, and the templates all keep working with zero modification. Never raises: any failure (model load error, inference error) logs and falls back to the original, unranked `chunks` list, same contract as the Sprint 5/6 services.
- **The cross-encoder model is lazily loaded on first call** (`_get_reranker_model()`), not at import time — unlike `embedding_service.py`'s eager `SentenceTransformer(...)` load at module import. `retrieval_service.py` imports `reranker_service` unconditionally, so an eager load there would pay the model download/load cost on every process start regardless of the flag; the lazy singleton keeps `ENABLE_RERANKER=False` completely free.
- When reranking is enabled, `retrieve_chunks()` over-fetches each source by `settings.RERANKER_CANDIDATE_MULTIPLIER` (default 3× the effective `top_k`) before merging, so the reranker has a real candidate pool to reorder instead of just re-scoring an already-truncated list; the final result is then reranked back down to the effective `top_k`. When the flag is off, retrieval depth and behavior are byte-for-byte unchanged from Sprint 6.
- No new third-party dependency — `CrossEncoder` ships inside `sentence-transformers`, already a dependency via `embedding_service.py`.

### Context Compression (Sprint 8) (`RAG/services/context_compression_service.py`)

Removes chunks from the retrieved set that are semantically redundant with one already kept, right before `answer_question()` builds the LLM context — off by default (`settings.ENABLE_CONTEXT_COMPRESSION`).

- `compress_context(chunks, similarity_threshold=None)` embeds each chunk's content with the existing `embedding_service.generate_embedding()` (no new dependency, no LLM call), walks the list in order, and drops a chunk only when its cosine similarity to an **already-kept** chunk is `>= similarity_threshold` (default `settings.CONTEXT_COMPRESSION_THRESHOLD`, `0.92`). The first occurrence of an idea always survives — only later duplicates are dropped — so no distinct fact is ever removed, just repetition. Fewer than 2 chunks is a no-op (nothing to compare). Never raises: an embedding failure logs and returns `chunks` unchanged, same never-raise contract as the rest of Sprints 5–7.
- Called from `query_service.answer_question()` immediately after `retrieve_chunks()` and before context/confidence/search-method/`QueryLog` are built, so every downstream consumer — the answer's context, `calculate_confidence()`, `describe_search_method()`, and the logged `sources` — reflects exactly what was compressed, never the pre-compression set.
- Threshold is deliberately conservative and opt-in: a too-aggressive value risks dropping a chunk that genuinely mattered, which is why this defaults off rather than joining Dynamic Top-K/Metadata Filtering as always-on despite also being local/free (no LLM call).

### Answer Generation (Sprint 9) (`RAG/services/{prompt_templates,citation_service}.py`, `llm_service.py`)

Prompt templates, grounding, citations, confidence, and hallucination reduction are one connected change to how the final answer is produced — unlike Sprints 6–8, all always active (no feature flag), since these are correctness/quality improvements to the core answer step rather than opt-in extras with a cost/risk tradeoff.

- **Prompt Templates** (`prompt_templates.py`) — `ANSWER_PROMPT_TEMPLATE` and `build_answer_prompt(context, question)` replace the inline f-string `llm_service.py` used to build itself. `NOT_FOUND_ANSWER` is the single canonical copy of the fixed fallback sentence, and `is_not_found_answer(answer)` is the one place that checks for it (a substring check, tolerant of minor whitespace variation) — `views.search_history` and `query_service.calculate_confidence()` both call it instead of keeping their own copy of the fallback text, closing the "keep them in sync" gotcha earlier CLAUDE.md revisions flagged.
- **Grounded Answers** — the template's rules restrict the model to the numbered sources only ("never use outside knowledge, even if you are confident it is correct"), require it to say what's missing rather than fill gaps itself when sources only partially answer, and require the exact fallback sentence, nothing else, when they don't answer at all.
- **Source Citations** (`citation_service.py`) — `build_cited_context(chunks)` numbers the (already retrieved/compressed) chunks `[1]..[N]` in order and renders each as a `(Document, chunk N)` labeled block; this numbered string *is* the `context` passed into `generate_answer()`, so the prompt's citation rule ("cite every claim as `[n]`") has something concrete to reference. `extract_citations(answer, chunks)` parses `[n]` markers back out of the generated answer, drops any out-of-range/invented number, dedupes repeats, and — for template convenience, the same "enrich the dict as it flows through" pattern `reranker_service.py` uses for `rerank_score` — annotates each cited chunk *in place* with `citation_number`. `ask_ai.html` reads that to badge cited source cards ("Cited [n]") and shows a citation count alongside confidence/response time/chunk count.
- **Confidence Score** — unchanged distance-based scoring (see the query pipeline steps above) plus two new signals folded into `calculate_confidence()`: the fallback answer forces `0`; zero citations despite retrieved sources discounts the score by 30% (not to `0` — short factual answers can legitimately cite sparsely). Both signals are opt-in via optional parameters, so the function's original one-argument call shape still behaves exactly as before.
- **Hallucination Reduction** is the combination of the above rather than one component: grounding rules + mandatory inline citations + `settings.ANSWER_TEMPERATURE` (default `0.2`, well below the Gemini default) to reduce improvisation + a confidence score that actually reflects whether the model grounded its answer in a citation, rather than only how strong retrieval looked.
- `llm_service.generate_answer(context, question)` keeps its exact pre-Sprint-9 signature and never-raise/error-string contract (`f"Gemini Error: {e}"` on failure, an unusual but long-standing behavior other code doesn't currently branch on) — only its internals changed: it now calls the multi-provider `llm_client` instead of configuring Gemini's `genai` itself (see the `LLM_MODEL` gotcha above, and the LLM Client section below), builds the prompt via `prompt_templates.build_answer_prompt()`, and passes `temperature=settings.ANSWER_TEMPERATURE` and `max_tokens=settings.ANSWER_MAX_TOKENS`.

### LLM Client (`RAG/services/llm_client.py`)

Multi-provider LLM access with fallback, sitting underneath `llm_service.py` (main Q&A), `graph_extraction_service.py`, `ai_tasks_engine_service.py`, and every other Gemini-era caller. `PROVIDER_REGISTRY` holds `GeminiClient`, `OpenRouterClient`, and `GroqClient` (the latter two share an `_OpenAICompatibleClient` base for OpenAI-format chat-completions REST calls); `LLMClient.generate()`/`generate_json()`/`generate_stream()` are the shared entry points every caller uses instead of talking to a provider SDK directly. See the `LLM_MODEL` settings gotcha above for the fallback/retry mechanics and env vars. `observability_service.save_trace()` reads `llm_client.get_last_llm_meta()` (which provider/model actually served the request) when persisting an `AIRequestTrace` — see Monitoring & Observability below.

### Background Task Execution (free-tier refactor) (`RAG/services/task_runner.py`, `RAG/tasks.py`)

Document processing and AI Tasks used to require a separate Celery worker process talking to a Redis broker — a hard requirement most free-tier hosts (Render free, Railway, Fly.io free allowance, PythonAnywhere) can't meet, since they only run a single always-on process. Both now dispatch onto an in-process `concurrent.futures.ThreadPoolExecutor` instead (`RAG/services/task_runner.py`) — no broker, no second process, no new dependency (`concurrent.futures` is stdlib).

- **`RAG/services/task_runner.py`**: a lazily-created, module-level `ThreadPoolExecutor` (`settings.BACKGROUND_WORKER_THREADS`, default `4`, worker threads). `submit(func, *args, key=None, **kwargs)` runs `func` on a pool thread — each pool thread calls `django.db.close_old_connections()` before and after (pool threads are reused across submissions, unlike a fresh Celery worker process per task, so stale DB connections must be dropped explicitly the same way Django's request lifecycle does it) and never lets an exception vanish silently (logs it, since nothing calls `.result()` on the returned `Future`). `key` (e.g. an `AITaskRun.id`) registers the `Future` in an in-memory registry so `cancel(key)` can later best-effort `Future.cancel()` it — only actually stops a still-*queued* task, the same real-world limitation Celery's `revoke(terminate=True)` had without a prefork pool. `get_status()` reports `{"available": True, "max_workers", "active", "pending"}` — `available` is always `True` once the module is importable, since unlike a separate Celery worker there's no "is it reachable" question; the pool lives in this same process.
- **Document processing**: unchanged behavior from before this refactor — off by default (`settings.ENABLE_ASYNC_PROCESSING`, `False`), so `upload_service.upload_document()`/`documents_view.document_embed` still process a document inline, in the request/response cycle, by default. When the flag is on, `document_embed`/`document_version_upload` dispatch `RAG.tasks.process_document_task` via `task_runner.submit()` instead. `Document.chunk_count` already defaults to `0` until `process_uploaded_document()` finishes, and `documents_view` already reads `chunk_count == 0` as `"Processing"` status, so this needed no UI/status-logic changes — a document just shows "Processing" for longer while a pool thread is running it.
- **`RAG/tasks.py`**: two plain functions (no decorator, no framework binding) — `process_document_task(document_id)` re-fetches the `Document`, calls `process_uploaded_document()`, and retries up to `MAX_PROCESSING_RETRIES` (3) times with exponential backoff + jitter (`time.sleep()` between attempts — safe since this runs on a background pool thread, not the request) on unexpected failure; after exhausting retries it logs and returns rather than raising. A `Document.DoesNotExist` (deleted before the task ran) is logged and treated as a no-op, not retried. `run_ai_task(run_id)` executes one `AITaskRun` end-to-end via `ai_tasks_engine_service.execute_run()`.
- **AI Tasks reliability**: `ai_task_create` *always* dispatches `run_ai_task` via `task_runner.submit(run_ai_task, run.id, key=run.id)`, regardless of `ENABLE_ASYNC_PROCESSING` — there's still no inline execution path, since a run can span up to `AI_TASKS_MAX_DOCUMENTS` documents. Unlike the old Celery-based design, though, this has **no missing-worker failure mode** — the pool lives in this same process, so AI Tasks now work out of the box on a single-process deployment where they previously couldn't run at all without a second, separately-started worker. `ai_task_cancel` calls `task_runner.cancel(run.id)` as a best-effort stop of a still-queued run; the real stop mechanism, unchanged, is the cooperative `AITaskRun.cancel_requested` flag `_call_llm_json()` polls between LLM calls. (`AITaskRun.celery_task_id`, which used to store a Celery `AsyncResult` id for this purpose, was removed via migration — the in-memory `run_id → Future` registry in `task_runner.py` replaces it.)
- **Caveat vs. a durable queue**: if the process restarts mid-task, that task is orphaned (stuck at `PENDING`/`RUNNING` with nothing resuming it) — the same risk profile the old Celery setup had with no result-backend recovery configured. Admin > System Logs already surfaces AI Task runs stuck at `PENDING` for over 2 minutes as a hint to re-run them.
- Django's cache (`CACHES`) no longer has a Redis-backed option — `LocMemCache` (Django's implicit default) is the only backend now, which is fine for the short-TTL, non-critical caches that use it (`context_processors.sidebar_status()`, the BM25/graph/retrieval caches, geolocation, system-config sync) — none of them need to share state across processes for correctness.

### AI Tasks (`RAG/services/{ai_tasks_engine_service,ai_tasks_prompts,ai_tasks_similarity_service}.py`)

A guided, multi-document batch-analysis workflow distinct from the Ask AI single-question pipeline — the UI flow is Select Task → Select Documents → Configure → Run → Review → Export (`/ai-tasks/`, `views.ai_tasks_view`). An `AITaskRun` is one of eight task types: Analyze Documents, Compare Documents, Summarize Documents, Extract Information, Validate Against Reference Documents, Find Similar Documents, Organize Documents, Generate Reports. Each maps to a `_run_<task_type>` handler in `ai_tasks_engine_service.py`'s `_HANDLERS` dict, dispatched by the never-raise `execute_run(run)` entry point (always ends the run `COMPLETED`/`FAILED`/`CANCELLED`). `AITaskRunDocument` links documents to a run with a `role` of `target` or `reference` (Validate, and optionally Analyze, take reference documents to check targets against). Results land in `AITaskResult` — one row per document, plus corpus-level synthesis rows (e.g. "Ranking Summary", "Comparison", "Executive Summary", "Compliance Overview", "Combined Table") for task types that produce a cross-document conclusion, not just per-document output.

- `settings.AI_TASKS_MAX_DOCUMENTS` (default 100) bounds both the per-document context budget math and the similarity clustering matrix size — the one setting that caps how large a single run can get.
- `ai_tasks_prompts.py` is a dedicated prompt-template module, structurally parallel to `prompt_templates.py` but separate: one `.format()` template + `build_..._prompt()` function per task-type LLM call, following the same grounding-rules + JSON-schema + `[n]`-citation convention and consuming `citation_service.build_cited_context()` output as context.
- `ai_tasks_similarity_service.py` backs Find Similar Documents and Organize Documents with pure-numpy embedding clustering — no re-embedding and no LLM call for the similarity math itself: `build_document_embedding()` mean-pools a document's existing `ChunkEmbedding` rows, `cluster_documents()`/`split_into_groups()` group them (threshold union-find / greedy farthest-point seeding for a target group count), and `similarity_to_centroid()` becomes `AITaskResult.score`. The LLM (`build_cluster_label_prompt`) is only used to *label* an already-computed group.
- Every run always executes on the background thread pool via `task_runner.submit()` (see Background Task Execution above) regardless of `ENABLE_ASYNC_PROCESSING` — there's no inline path, since a run can span up to `AI_TASKS_MAX_DOCUMENTS` documents.
- `queries_service.py` is unrelated to AI Tasks despite the naming proximity to `query_service.py` — it backs **Admin > Queries**, a workspace-wide search/filter/analytics view over existing `QueryLog` rows (`filter_and_sort_queries()`, `get_queries_analytics()`), and runs no retrieval or LLM call of its own. A `q` content-text filter is separately gated by a permission check so viewing query *metadata* and viewing query *content* (the actual question/answer text) can be granted independently.

### Deployment (free-tier)

The stack is designed to run entirely on $0/free-tier infrastructure:

- **Backend**: any host that keeps one process alive continuously — Render's free web service, Railway, Fly.io's free allowance, or PythonAnywhere all work, since the app no longer needs a second worker process or a message broker.
- **Database + pgvector**: a hosted Postgres with the `vector` extension available — **Neon.tech** or **Supabase** both offer a free tier that supports `CREATE EXTENSION vector`. `docker-compose.yml`'s `postgres` service is for local dev only.
- **File storage**: defaults to local filesystem (`MEDIA_ROOT`) unless `USE_S3_STORAGE=True`, in which case `settings.py` swaps `STORAGES["default"]` to `storages.backends.s3.S3Storage` (django-storages) pointed at `AWS_S3_ENDPOINT_URL` — any S3-wire-compatible provider works (Supabase Storage, Cloudflare R2, actual AWS S3), not just AWS. `AWS_S3_ADDRESSING_STYLE = "path"` is required for Supabase/most non-AWS S3-compatible endpoints. `AWS_DEFAULT_ACL = None` (the bucket's own policy decides public/private — see `DEPLOYMENT.md` for making it public-read) and `AWS_QUERYSTRING_AUTH = False` (plain URLs, no expiring-signature query strings) are deliberate choices for a public document-serving bucket. `AWS_S3_FILE_OVERWRITE = False` matches `FileSystemStorage`'s own default (a same-named upload gets a suffixed filename rather than clobbering). Enabling S3 storage is what removes the earlier caveat about avoiding hosts with an ephemeral filesystem (e.g. Render's free web service) — without it, that caveat still applies.
- **LLM providers**: OpenRouter/Groq/Gemini (`RAG/services/llm_client.py`) are all free-tier-capable already — no change needed.
- **Caching**: `LocMemCache`, no separate service to provision.

### Monitoring & Observability (Sprint 10 + later) (`RAG/services/{health_service,trace,perf,observability_service,error_intelligence_service,rate_limit_service}.py`)

- **Logging**: `settings.py` now has an explicit `LOGGING` dict (console handler, `%(asctime)s %(levelname)s %(name)s: %(message)s`), so the `logger.info()`/`logger.exception()` calls already present throughout `RAG/services/*.py` actually surface — previously they relied on Django's implicit default, which only shows `WARNING`+ on the root logger. `DJANGO_LOG_LEVEL` controls the root level (default `INFO`); `httpx`/`httpcore`/`urllib3` are pinned to `WARNING` since the embedding/reranker model libraries' Hugging Face requests would otherwise log a line per HTTP call and drown out everything else.
- **`GET /health/`** (`views.health_check`, public — no `@login_required`, since a health check has to work before anything else does) returns JSON via `health_service.get_health_status()`: `200` with `{"status": "ok", ...}` or `503` with `{"status": "degraded", ...}`. Reuses `stats_service.get_system_status()` for the DB/pgvector checks rather than duplicating that `SELECT 1`/`pg_extension` lookup, but wraps the whole call — `get_system_status()`'s own unguarded ORM `.count()`/`.aggregate()` calls (below its `SELECT 1` try/except) will raise on a fully-down database, which is fine for an authenticated page but not acceptable for a public health endpoint that has to stay up precisely when the database might not be. Checks `_check_background_jobs()` (`RAG.services.task_runner.get_status()`), which is unconditionally load-bearing to the overall `ok`/`degraded` verdict — unlike the old Redis/Celery-worker check it replaced, there's no "only matters if a flag is on" carve-out, since the background thread pool backs AI Tasks unconditionally.
- **Request tracing** (`trace.py`) — a lightweight, no-middleware tracer built on `contextvars`: `new_trace_id()`/`bind_trace_id()` set a per-context trace id, `record_stage()`/`get_stages()` accumulate named timing stages. `TraceIdLogFilter` is registered in `settings.LOGGING` so every log line carries the active trace id. Wired explicitly at specific call sites (e.g. `views.ask_ai` calls `bind_trace_id()` directly) rather than globally via middleware — only the request paths that actually need a trace (Ask AI, AI Tasks) pay for one.
- **Stage timing** (`perf.py`) — `timed_stage(label, **context)` is a context manager used throughout the retrieval/query/LLM pipeline (vector search, BM25, graph retrieval, HyDE, multi-query, reranking, context compression, LLM calls): it logs a `[PERF]`-prefixed line to the `"RAG.perf"` logger *and* calls `trace.record_stage()`, so every timed block becomes a queryable trace entry with no call-site-specific plumbing. `Timer` is the non-logging variant for capturing a duration as a value.
- **Trace persistence & LLM observability** (`observability_service.py`) — `save_trace()` builds an `AIRequestTrace` row from `trace.get_stages()` plus `llm_client.get_last_llm_meta()` (which provider/model actually served the request, after any fallback), called from `query_service.py` (every Ask AI question) and `RAG.tasks.run_ai_task` (every AI Tasks run). The read side (`list_traces`, `get_performance_summary`, `get_recent_provider_status`, `get_filter_options`) backs the admin-only "AI Logs" tab of `views.admin_system_logs_view`.
- **Error intelligence** (`error_intelligence_service.py`) — `ErrorCaptureHandler`, a `logging.Handler` registered in `settings.LOGGING` alongside the console handler, so every `logger.warning`/`error`/`exception` call app-wide is automatically grouped into `ErrorGroup` rows (after `redact_secrets()` scrubs the message) with zero call-site changes anywhere else in the codebase. Surfaced on the same `admin_system_logs_view`'s Error Groups tab, and consumed by `health_service` for a "recent errors" signal.
- **Rate limiting** (`rate_limit_service.py`) — a `django.core.cache`-backed (so `LocMemCache`-backed) fixed-window counter (`is_rate_limited(key, limit, window_seconds)`) plus cooldown helpers (`start_cooldown()`/`get_cooldown_remaining_seconds()`), fails open on cache errors. Not used for LLM calls or retrieval — it protects auth-adjacent endpoints only: login attempts (per-username and per-IP), signup, password-reset requests, and OTP resend/verify, all with limits hardcoded in `auth_views.py`/`otp_service.py` rather than settings — see Notifications & Verification below.
- **`admin_system_logs_view`** ties the above together as the closest thing this app has to a centralized log viewer: Activity (from `ActivityLog`, see Activity Logging below), AI Logs (from `AIRequestTrace`), and Error Groups tabs in one admin-only page, gated by RBAC permissions (`system.view_ai_logs`, `has_any_system_logs_permission`) rather than `is_staff` — see Access Control (RBAC) below.

### Data model (`RAG/models.py`)

`Document` (owned by `User`, holds `file_hash` for dedup, `file_size`, `file_type`, denormalized `chunk_count`) → `DocumentChunk` (ordered by `chunk_number`) → `ChunkEmbedding` (1:1 with a chunk, `VectorField(dimensions=settings.EMBEDDING_DIMENSION)` plus which model produced it — see the dimension-mismatch gotcha above). `QueryLog` is independent of the document graph and records every Q&A interaction per user. `Entity`, `EntityMention`, and `Relationship` form the knowledge graph — see below.

Beyond the core RAG pipeline, several later model families extend `Document`/`User` without touching the pipeline itself: `Tag`/`Category`/`Collection`+`CollectionDocument`/`Favorite`/`DocumentShare` (document organization and sharing, see Document Organization below); `Role`/`Permission`/`UserRole`/`SystemConfiguration` (access control, see Access Control (RBAC) below); `EmailOTP`/`Notification`/`NotificationPreference`/`ActivityLog` (verification, inbox, and audit trail, see Notifications, Verification & Activity Logging below); `AITaskRun`/`AITaskRunDocument`/`AITaskResult`/`AIRequestTrace`/`ErrorGroup` (AI Tasks and observability, see the AI Tasks and Monitoring & Observability sections above).

### Access Control (RBAC) (`RAG/services/permission_service.py`, `RAG/decorators.py`, `RAG/middleware.py`)

A real, DB-backed role/permission system, added after the nav's original `is_staff`-only gate (see the Information architecture note below — that description is now superseded for admin-area access). The two are deliberately kept separate rather than merged:

- **`Permission`** — a grantable capability, `codename` unique and namespaced (`"<area>.<action>"`, e.g. `"users.suspend"`, `"system.view_ai_logs"`, `"queries.view_content"`, `"pages.ai_tasks"`).
- **`Role`** — a named bundle of `Permission`s via M2M; `is_system` flags built-in seeded roles. `has_permission(codename)` hardcodes a bypass for the Admin role slug — Admin always passes every check regardless of what's actually in the M2M table. There is no separate "Super Admin" tier; Admin is the sole top-tier role.
- **`UserRole`** — a `OneToOneField` to `User`: one active role per user, not stackable.
- **`permission_service.py`** is the single source of truth for every check: `is_admin`, `user_has_permission`, `has_admin_area_access`, `has_any_settings_permission`, `has_any_system_logs_permission`, plus a "privilege-escalation guards" group (`is_last_admin`, `can_actor_assign_role`, `can_actor_manage_target_user`, ...) that stops a non-Admin from granting itself Admin-level access or removing the last remaining Admin.
- **`RAG/decorators.py`** wraps these into view decorators — `role_required`, `permission_required(*codenames)`, `admin_required`, `admin_area_required`, `settings_access_required`, `system_logs_access_required` — used throughout `RAG/views.py` in place of ad-hoc `is_staff`/`is_superuser` checks.
- **`RoleBasedAccessMiddleware`** (`RAG/middleware.py`) is a coarse defense-in-depth backstop over the whole `/admin/` URL prefix, checking `has_admin_area_access()` rather than `is_staff`.
- **Django Admin is also RBAC-gated**, not left on Django's own `is_staff`/`is_superuser` semantics: `RBACAdminOnlyMixin` and `RBACScopedModelAdmin` (`RAG/admin.py`) gate custom `ModelAdmin`s via `permission_service.is_admin()`/`user_has_permission()` specifically because a Django `is_superuser` account (e.g. one made with `createsuperuser`) would otherwise bypass RBAC entirely through `/admin/`. `Role`/`Permission`/`UserRole` each have their own RBAC-gated `ModelAdmin`, with `save_related`/`save_model` re-enforcing the same privilege-escalation guards so Django Admin can't be used as a bypass route. `SystemConfiguration` has no Django Admin registration — it's only editable through the app's own Settings page.
- **`SystemConfiguration`** (singleton, `pk=1`) is a DB-backed, admin-editable settings layer that sits *alongside* `settings.py`, not instead of it: `system_config_service.apply_config_to_settings()` monkey-patches live values (e.g. `TOP_K`, `ENABLE_HYDE`, `CHUNK_SIZE`, `LLM_PROVIDER`, the reranker/compression flags — the full list is `MANAGED_SETTINGS_FIELDS`) onto `django.conf.settings`, so every existing `settings.X` read elsewhere in the codebase is unaffected by this feature's existence. `SystemConfigSyncMiddleware` calls a 15-second-cached `apply_config_to_settings_cached()` on every request to keep multi-worker deployments in sync without a DB hit per request. `save_config(data, user)` enforces per-field RBAC (only permissions the submitting user actually holds get applied) plus range/cross-field validation, then invalidates the cache and resets the LLM client so an editor's own next request already reflects the change.

### Knowledge Graph (`RAG/services/graph_*.py`)

Built during upload, read during query answering. All three models are scoped per `User`.

- **`Entity`** — a deduplicated entity, keyed by `(user, name, entity_type)` where `name` is the lowercased/whitespace-normalized form (`display_name` keeps original casing for UI). `entity_type` is a free-form string (not Django `choices`), so new types need no migration; `graph_extraction_service.SUGGESTED_ENTITY_TYPES` is prompt guidance only. `mention_count` is denormalized, incremented on each new `EntityMention`.
- **`EntityMention`** — links an `Entity` to the `DocumentChunk` it was found in (`unique_together`, so re-processing a chunk is a no-op). This is what graph retrieval joins through to get back to chunk content.
- **`Relationship`** — a directed edge `(user, source, target, relation_type)`. Re-extracting the same triple from another chunk doesn't create a duplicate row — it increments `weight` via `get_or_create` + `F("weight") + 1`. `context` stores the first supporting chunk snippet (up to 500 chars) for reference.

**Extraction** (`graph_extraction_service.extract_graph()`) is a single Gemini call per chunk (JSON-mode response, `response_mime_type: "application/json"`) that returns both entities and relationships together, rather than two calls — the prompt requires relationship endpoints to reuse the exact entity names given, and `_parse_response()` drops any relationship referencing a name outside the extracted entity list. Chunks under `MIN_CHUNK_LENGTH` (20 chars) are skipped without an API call. **Never raises** — any failure (missing API key, network error, malformed JSON) logs and returns an empty result, by design, so graph enrichment can never break ingestion or query answering. It reuses `gemini_client.get_model()`, the same shared factory `llm_service.py` was moved onto in Sprint 9 (see the `LLM_MODEL` gotcha above).

**Construction** (`graph_service.build_graph_for_chunk()`) calls `extract_graph()` *outside* any DB transaction (it's a slow network call), then writes the results inside a separate `@transaction.atomic` block (`_persist_graph()`) so a DB transaction is never held open across the LLM round-trip. Called once per chunk from `upload_service.upload_document()`, right after that chunk's embedding is saved.

**Retrieval** (`graph_retrieval_service.graph_search()`) does *not* run a second LLM extraction per query (cost/latency). Instead it lexically matches the question against the user's already-known `Entity.name` values (same "load everything into Python, score it" style as `bm25_service.py`), expands one relationship hop via `Relationship`, then returns the `EntityMention`-linked chunks — shaped identically to `vector_search()`/`bm25_search()` results (`search_type: "graph"`) so `retrieval_service.retrieve_chunks()` merges them with zero special-casing.

No new third-party dependencies were introduced — extraction reuses `google-generativeai`, already a dependency for `llm_service.py`.

### Notifications, Verification & Activity Logging (`RAG/services/{notification_service,otp_service,email_service,activity_log_service,profile_completion_service,device_intelligence_service,geolocation_service}.py`)

- **Email OTP verification** (`EmailOTP` model, `otp_service.py`) is signup email verification only — not password reset (which uses its own email template, not `EmailOTP`) and not 2FA. `auth_views.signup()` creates the `User` with `is_active=False` and calls `otp_service.generate_and_send_otp()`; `verify_otp()` activates the account and sets `UserProfile.email_verified`; `resend_otp()` and `login_user()`'s "unverified vs. admin-suspended" branch both go through `otp_service.has_pending_verification()`/`can_resend()`. `rate_limit_service.py` caps OTP resend frequency and verify attempts.
- **`email_service.send_templated_email()`** is the one function in the codebase that calls `django.core.mail` — used by OTP send, password reset, notification emails, and sharing invites, always dispatched through `task_runner.submit()` (see Background Task Execution above) so a slow SMTP call never blocks the request.
- **`Notification`/`NotificationPreference`** are a recipient-keyed inbox (bell/dropdown in `base.html`, a Notification Center page), explicitly distinct from `ActivityLog` below — `notification_service.create_notification()` is called from document-sharing, profile/security, and account-verification events.
- **`ActivityLog`** is a separate, actor-keyed, admin-facing audit trail — not a replacement for `QueryLog`, which remains its own model for Q&A history/analytics. `activity_log_service.log_activity()` records a namespaced `action` string (e.g. `"document.deleted"`) plus IP/user-agent/geolocation, called explicitly from dozens of sites in `views.py` (document actions, role changes, profile updates, auth events) and generically via `RequestActivityMiddleware` (`RAG/middleware.py`) for any request that didn't already log something more specific. Backs the Activity tab of `admin_system_logs_view` (see Monitoring & Observability above).
- **`profile_completion_service.get_completion(user, profile)`** computes a real completion percentage from 12 equal-weight `UserProfile`/`User` fields (avatar, headline, phone, department, skills, LinkedIn, etc.), returning `{percent, filled, total, missing, recommendations}` — shown on the profile page, not a fabricated placeholder.
- **`device_intelligence_service.py`** derives login history, active sessions, online status, and account health from real captured data (`ActivityLog` rows' IP/user-agent, plus Django's DB-backed `Session` table) — no mocked device list. **`geolocation_service.py`** resolves an IP to coarse city/region/country (cached 24h) and is what `activity_log_service.py` calls to enrich each `ActivityLog` row; `device_intelligence_service.get_login_history()` reads that geolocation data back out for display. Together these back the "active sessions" / "login history" / "current device" panels on the profile page — this is the "multi-device session listing on Profile" the Information architecture note below used to list as unbuilt.

### Document Organization (`RAG/services/{tags_service,categories_service,collections_service,favorites_service,sharing_service,document_access_service,document_library_service,preview_service}.py`)

Tags, Collections, and Favorites — listed in the Information architecture note below as unbuilt placeholders in an earlier revision of this doc — now have real backing models, services, views, and templates; that placeholder note is stale for these three (see the corrected note below).

- **`Tag`** (user-scoped, unique on `(user, slug)`, multi-valued per document) and **`Category`** (also user-scoped, but single-valued per document — a sibling of Tag with the same shape, one assignment instead of many) each have their own service (`tags_service.py`, `categories_service.py`) and are wired into `documents_view`/bulk document actions.
- **`Collection`** + **`CollectionDocument`** (`collections_service.py`) are user-defined groupings of documents (list/create/rename/delete/add/remove), with their own templates (`documents/collections.html`, `documents/collection_detail.html`).
- **`Favorite`** (unique on `(user, document)`, `favorites_service.py`) is a simple per-user star/unstar with its own template (`documents/favorites.html`).
- **`document_access_service.py`** is the single read/authorization layer: `get_accessible_document_ids(user)` unions owned documents ∪ Organization Library documents (`is_org_library=True`) ∪ directly-shared documents ∪ documents shared via the user's `Role`; `can_view_document`/`can_edit_document` (edit is owner-only) fail closed for an unauthenticated/`None` user.
- **`sharing_service.py`** is the write/mutation layer for one specific access path — creating/listing/revoking `DocumentShare` rows, which can target a specific user, a `Role`, or a pending email invite (converted to a real share once that email verifies via OTP). `document_access_service` is what actually *reads* `DocumentShare` to decide visibility; `sharing_service` only owns writing it.
- **`document_library_service.py`** provides `filter_and_sort_documents()` (search/status/type/category/tag/date/archived filtering and sorting) and `annotate_document_status()` (Pending/Processing/Partial/Ready/Archived + percent + formatted size) — `documents_view` is now built on these rather than the ad-hoc on-the-fly status logic an earlier revision of this doc described.
- **`preview_service.get_document_preview_text()`** is a plain-text excerpt (reuses `text_extractor.extract_text()`, truncated to 10,000 chars), not a rendered PDF/DOCX viewer — no new rendering dependency.
- **`partials/_coming_soon.html`** now has zero remaining `{% include %}` callers anywhere in the codebase — it's dead code kept only for a future placeholder need. Of the items an earlier revision of this doc listed as pending behind it: Collections/Tags/Favorites (above), multi-device session listing on Profile (`device_intelligence_service`, see Notifications & Activity Logging above), and a centralized log viewer on Monitoring (`admin_system_logs_view`, see Monitoring & Observability above) are now all real. Saved Searches on AI Search and scheduled/comparative Reports remain unimplemented — they simply don't render the placeholder partial either, they just don't exist yet.

### Views (`RAG/views.py`)

Function-based, one view per page (not a single multiplexed dashboard):

- `dashboard` — aggregate stats (`stats_service.get_dashboard_stats`), a 7-day activity/search-mix/chunk chart snapshot (`get_analytics_data`), and (Enterprise Dashboard rebuild) real Smart Insights / Recommendations (`get_dashboard_insights`) plus a Quick Actions row.
- `ask_ai` — dedicated Q&A page ("AI Search" in the nav); POSTs a question (plus an optional `document_id` from a "Search in" dropdown, parsed into `RetrievalFilters` — Sprint 6 metadata filtering), shows answer/sources/confidence/timing, plus Suggested Questions derived from the user's own top knowledge-graph entities.
- `documents_view` — upload (via `upload_service`) + document library, with a per-document status computed on the fly (`Processing` / `Partial` / `Embedded`) by comparing `chunk_count` against the count of chunks that actually have an embedding.
- `document_delete`, `search_history` (paginated, 15/page), `analytics_view` (14-day charts, now including confidence/response-time trends), `profile_view` (profile + password-change forms + current-session info).
- `knowledge_base_view`, `entity_detail_view`, `relationships_view`, `knowledge_graph_view`, `citation_explorer_view` — the Knowledge Base section (new UI surface for Sprint 5's Entity/Relationship graph — see below).
- `reports_view`, `export_documents_report`, `export_usage_report` — real CSV exports (`reports_service.py`, stdlib `csv`, no new dependency).
- `monitoring_view` — **replaces the old `settings_view`/`/settings/` route.** Same RAG-pipeline-config + DB/pgvector content as before, now also showing background task pool health (see Background Task Execution above). Originally gated behind `request.user.is_staff`; now gated by RBAC (`settings_access_required`/`has_any_settings_permission`, see Access Control (RBAC) above) rather than `is_staff` directly — see the corrected Information architecture note below.
- `admin_queries_view`/`admin_query_detail_view` — Admin > Queries, backed by `queries_service.py` (see the AI Tasks section above for how it differs from `query_service.py`).
- `admin_system_logs_view` — the Activity / AI Logs / Error Groups tabbed admin page described in Monitoring & Observability above.
- `ai_tasks_view`/`ai_task_create`/`ai_task_status`/`ai_task_results`/`ai_task_history`/`ai_task_cancel`/`ai_task_delete`/`ai_task_export` — the AI Tasks wizard and history described in the AI Tasks section above, gated by `@permission_required("pages.ai_tasks")`.
- `health_check` (Sprint 10) — the one view in this list that's public (no `@login_required`); see the Monitoring & Observability section above.

`stats_service.py` centralizes all aggregate/chart-data queries (`get_dashboard_stats`, `get_recent_activity`, `get_analytics_data`, `get_dashboard_insights`, `get_system_status`) — reuse it rather than writing new aggregate queries directly in views. `knowledge_service.py` does the same for Knowledge Base queries (Entity/Relationship/EntityMention), and `reports_service.py` for CSV row-building.

`context_processors.py` runs two context processors on every authenticated page render (registered in `TEMPLATES.OPTIONS.context_processors`): `sidebar_status` (merged recent-activity feed + `get_system_status()`, cached 30s) and `breadcrumbs` (a static `BREADCRUMB_MAP`/`NAV_GROUP_MAP` keyed off `request.resolver_match.url_name` — see below). Neither needs any individual view to build its own trail/status for the common case.

### Information architecture & role-based navigation

The nav is a grouped, multi-page sidebar (`templates/partials/sidebar.html`), not a single dashboard: Dashboard → Workspace (Documents, Knowledge Base, AI Search, AI Tasks) → Insights (Analytics, Reports) → Profile, plus an **Administration** group (Monitoring, Queries, System Logs, Users/Roles) gated by RBAC rather than `request.user.is_staff`. `is_staff` was the original seam this note described before Access Control (RBAC) (see above) was built — it's now superseded: admin-area visibility is driven by `permission_service.has_admin_area_access()`/per-page permission checks, and Django's own `is_superuser` is deliberately *not* trusted for the app's custom admin pages (only for Django Admin, which is itself RBAC-gated — see above) so a `createsuperuser` account can't bypass RBAC.

- **Breadcrumbs** (`partials/_breadcrumbs.html`) come from `context_processors.breadcrumbs()`'s `BREADCRUMB_MAP` (`{url_name: [(label, url_name_or_None), ...]}`). A view with a dynamic final segment (e.g. `entity_detail_view` showing the entity's actual name) sets `breadcrumb_leaf` in its own context instead of trying to fit a dynamic value into the static map.
- **Active nav highlighting** for a section with more than one URL (e.g. every Knowledge Base sub-page) goes through `NAV_GROUP_MAP` in the same context processor, producing `active_nav` — `_nav_item.html` compares against that, not the raw `url_name`, so `entity_detail`/`relationships`/`knowledge_graph`/`citation_explorer` all highlight "Knowledge Base".
- **Command palette** (`partials/_command_palette.html`, included globally in `base.html` for authenticated users) — Cmd/Ctrl+K, a client-side Alpine component listing the exact same `{% url %}`-resolved destinations as the sidebar. No new backend, no search index — it's keyboard navigation, not a search feature.
- Most sections once listed here as unbuilt placeholders behind `partials/_coming_soon.html` are now real (Collections/Tags/Favorites, multi-device session listing, a centralized log viewer) — see the note at the end of Document Organization above for what's still actually missing (Saved Searches on AI Search, scheduled/comparative Reports) and the partial's current dead-code status.

### Knowledge Base (new UI, Sprint 5 backend) (`RAG/services/knowledge_service.py`, `templates/knowledge/`)

The Knowledge Graph (`Entity`/`EntityMention`/`Relationship`, built during upload since Sprint 5) had no UI at all until this rebuild — `knowledge_service.py` is read-only, user-scoped, and is the first thing that surfaces it. Four sub-pages share one tab bar (`partials/_kb_tabs.html`) under a single "Knowledge Base" sidebar entry rather than four separate top-level nav items:

- **Browse** (`knowledge_base_view`) — category/search-filterable entity grid (`search_entities()`), overview counts (`get_knowledge_overview()`).
- **Relationship Explorer** (`relationships_view`) — paginated table of `Relationship` rows, most-reinforced (`weight`) first, filterable by `relation_type`.
- **Graph** (`knowledge_graph_view`) — a `vis-network` (CDN, loaded only on this page — see Performance below) force-directed visualization. `get_graph_data()` caps at `GRAPH_NODE_LIMIT` (120) entities by mention count; this is a visualization, not an export, so the Relationship Explorer table is the place for the full unfiltered list. `get_graph_insights()` (most-mentioned entity, most-connected entity by relationship degree, top category/relation type) backs the stat cards above the graph.
- **Citation Explorer** (`citation_explorer_view`) — built from `QueryLog.sources` entries with a `citation_number` (Sprint 9's per-answer citations), *not* a separate citations table — citations are already fully captured there.

`entity_detail_view` (reached by clicking an entity, not from the sidebar) shows its mentions (linking back to source chunks) and one-hop outgoing/incoming relationships.

### Reports (`RAG/services/reports_service.py`)

Two real CSV exports (`export_documents_report`, `export_usage_report`) writing straight into the `HttpResponse` via the stdlib `csv` module — no new dependency, no intermediate file. `reports_service.py` only builds the row lists (easy to unit test); the views own the `HttpResponse`/`csv.writer` plumbing.

### Templates & frontend

Templates live in `templates/` (`base.html` + `templates/partials/`, plus `templates/knowledge/` for the Knowledge Base sub-pages), configured via `TEMPLATES.DIRS` rather than per-app template dirs. Tailwind, Alpine.js, Lucide icons, and Chart.js are all loaded via CDN `<script>` tags in `base.html` / per-page `extra_scripts` blocks — there is no npm/node build step for frontend assets. `vis-network` (Knowledge Graph visualization) follows the same CDN pattern but is loaded *only* from `knowledge/graph.html`'s own `extra_scripts` block, not globally — the closest equivalent this architecture has to route-based code splitting. Chart data is passed from views as Python lists/dicts and serialized into the page with Django's `json_script` filter, then read by inline Chart.js setup code (see `dashboard.html`, `analytics.html`).

Reusable partials worth knowing about beyond the obvious (`_nav_item`, `_stat_card`): `_page_header.html` (title/subtitle/optional CTA), `_empty_state.html`, `_coming_soon.html` (see above), `_logo.html` (the brand mark — a three-node network glyph, `currentColor`-driven so it doubles as a monochrome mark; used in the sidebar, topbar mobile view, login/signup, and baked into the favicon data URIs since those can't use `currentColor`). `_stat_card.html` takes an optional `numeric=True` to animate the value counting up from 0 on page load (Alpine `requestAnimationFrame`, ~700ms) — only pass it for genuinely numeric values, not formatted strings like "4.2 MB".
